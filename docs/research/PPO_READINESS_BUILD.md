# PPO launch readiness build

Prospective scope, 2026-09-11. The user requested a working system ready for PPO
training. This build opens no registered training, development or held-out seed.
It preserves the frozen three families, five optimizer seeds, task, rewards,
controller information and selection gates.

## Source-freeze work

1. Add a read-only product projection of closed, production-admitted training
   custody. Retain every slot and failure; show rollout objectives, resource
   costs and multipliers. The server reads a bounded public export, never live
   training logs or an arbitrary checkpoint. File integrity is distinct from
   source admission and from evidence of useful learning.
2. Prepare an offline, single-attempt PPO recording producer through the existing
   four-target adapter, minute dispatcher, guard and public frame projection.
   Fix the presentation policy now: final PI-Lagrangian optimizer seed 101,
   fixture 9,000,034, 168 hours, 20-minute execution cap, no replacement if that
   slot fails admission. This is a descriptive trajectory, never a selected
   winner. Running it later requires explicit rehearsal authorization after
   training custody closes. The HTTP controller choices remain H and MPC.
3. Preserve research E-beta and its negative fixture results. The separate product
   MPC and the PPO presentation trajectory cannot replace the research comparator
   or establish daily-return feasibility. Inspect existing saved evidence only;
   do not repeat comparator experiments or change selection to obtain a success.
4. Measure lossless compression of existing saved capacity archives, if useful,
   without a plant reset, new inference, optimizer step or deletion. Change the
   archive implementation only if measured savings justify it and compatibility
   and detached verification remain covered. Otherwise retain conservative
   evaluation caps and state the external storage requirement explicitly.
5. Run focused fixture tests, the complete Python suite, strict typing/formatting
   for changed Python, compilation, CLI imports, frontend build/lint and browser
   inspection. Keep the implementation revision clean during the final gate.

Unit/integration fixtures may use disposable seeds, synthetic custody dependencies
and tiny fixture-trained models; they remain visibly ineligible as registered
evidence. No new capacity training campaign or full-week controller rehearsal is
part of this build. Raw data stays outside tracked files. Record all failures and
checks in the journal and compact results.

## Launch decision

Present the exact clean implementation, host, 15-cell matrix, external root and
training budget for approval. Training admission needs 5 GiB free; evaluation has
a separate, larger reserve and later authority. Do not create the canonical
training authorization or campaign root during readiness work. The authorization
commit must have the approved implementation as its sole parent and pass its own
clean gate. The registered campaign then runs once, without outcome inspection
between cells. Development and held-out remain separately gated.

Training readiness means the fixed experiment can run and retain an auditable
negative result. It does not mean PPO will learn an admissible controller or that
E-beta will satisfy its hard return constraints. Those risks must accompany the
launch decision, not be hidden by the product's operating MPC.
